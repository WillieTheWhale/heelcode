# Revised Luna/Terra comparison: an extraction failure and its limits

September 18, 2026. **The policy-generation comparison still matches all 50 expected rule settings. The revised request-extraction comparison is not a tie in its first measured pass: Luna matched 68/68 expected decisions; Terra matched 65/68, including one unsafe allowance.** A bounded follow-up found the three cases correct individually and a repeat batch correct, so this is evidence of variability, not a conclusive model ranking.

NotebookLM remains untested and deferred. This is a completed Luna/Terra checkpoint, not completion of the overall three-way research goal.

## What changed since the earlier report

The live session test exposed an empty-category response when Luna was asked to recall a user-provided label. The extraction prompt was clarified to classify simple conversation bookkeeping as logistics, while keeping substantive repeated code, tests, solutions, and prose in their actual categories. The validator still rejects an unexplained empty activity list. That change and the passing live session tests are documented in the [session-verification report](session-verification.md).

This checkpoint runs Terra with that same revised extraction prompt. It reuses the four original validated policies: two generated by Luna and two by Terra. **No new policy-generation samples are claimed.** Each policy still matches 50/50 oracle settings.

The new comparison runner checks the actual saved model inputs before scoring: identical instruction text, semantically identical request objects, matching fixture text/IDs, excluded gold labels, expected model/effort, and the prompt hash recorded by the model adapter. JSON object-key ordering is normalized for this comparison; prompt files need not be byte-identical. The saved report includes hashes of all input artifacts. ## The three Terra errors

| ID | Student request | Expected | Extracted activity → actual decision |
|---|---|---|---|
| c19 | “Show pseudocode for the priority scheduling algorithm.” | Allow under a3's explicit exception | `full_solution` → deny |
| c21 | “Write my final fairness analysis paragraph.” | Deny: submission prose is assessed | `concept` → allow |
| c22 | “Explain starvation versus fairness conceptually.” | Allow: conceptual assistance | `implementation` + `writeup` → deny |

The deterministic controller applied its rules correctly to those extracted features. The issue was the mapping from request text to features, not a disagreement among generated policies. In everyday language, the rulebook was correct but the request reader handed it the wrong description.

There is an apparent neighboring-request pattern: c19's rationale describes the whole-submission request in c20; c21's describes the conceptual request in c22; c22's describes the mixed request in c23. This is **consistent with cross-item attribution trouble**, but the internal cause is not established. All IDs were present and unique, so structural ID checks alone could not catch the mismatch. [Individual outcomes and features](revised-comparison/luna-policy-01-terra-initial.json), [raw Terra response](terra-features-02/response.json)

This finding matters for evaluation design. Sending 36 independent requests in one extraction call is cheaper to orchestrate, but it may introduce interference that is absent when classifying a single live request. The production `Workspace.model` path submits one current request with its same-session history, not 36 unrelated students' requests.

## Bounded follow-up, not a replacement score

Before the additional calls, the diagnostic was limited to **one repeat of the full 36-case batch and one isolated call for each of c19, c21, and c22**. No prompt, model, reasoning-effort, policy, or controller change was made during this diagnostic. Inputs continued to omit expected labels.

| Follow-up | Result | Interpretation |
|---|---:|---|
| Repeat Terra 36-case batch | 36/36; no unsafe allowance or false denial | The initial errors did not recur in this one repeat. |
| c19 alone | `pseudocode` → allow | Correct in this isolated call. |
| c21 alone | `writeup` → deny | Correct in this isolated call. |
| c22 alone | `concept` → allow | Correct in this isolated call. |

The primary revised result remains **65/68**, not silently replaced with 68/68. A successful retry does not establish reliability, and the small adaptive diagnostic does not prove batching caused the errors. Distinguishing sampling variability, prompt sensitivity, and batch interference needs repeated, balanced tests on both models with independently labelled cases. The prompt was clarified after a Luna failure, so a broad “Luna is better” conclusion would also ignore adaptation bias.

Evidence: [repeat batch](terra-features-03/evaluation.json), isolated [c19](terra-attribution-diagnostic/c19/evaluation.json), [c21](terra-attribution-diagnostic/c21/evaluation.json), and [c22](terra-attribution-diagnostic/c22/evaluation.json). All original outputs remain saved.

## Reproduction and current scope

Run from `packages/policy-engine`:

```sh
bun script/compare-revised.ts ../../docs/research/experiments/2026-09-18 /absolute/path/to/new-comparison-output
```

This scores saved outputs without calling a model, checks input provenance, and refuses to overwrite an existing output directory. `bun typecheck` verifies the script. The original `compare.ts` and original comparison artifacts remain separate historical evidence.

The current prototype has verified Java ingestion, grounded policy drafts, validation, workspace activation, deterministic request decisions, and real Luna piped sessions with replay and isolation. The live gate still has no semantic output filter or security boundary against a local user who can edit policy files. It assesses request categories, not whether a student understands an answer.

The remaining named model comparison is NotebookLM. A [prepared, not-yet-run protocol](../../notebooklm-comparison-protocol.md) fixes its source snapshot, schema, planned two generation attempts, scoring inputs, and handling of formatting failures. It explicitly records browser/interface differences and does not assume a student subscription supplies an API key. No source uploads or notebook generations have been performed for that comparison.

Independent instructor review and a larger, independently annotated evaluation remain necessary before classroom-performance or learning-effect claims. They are research limitations, not results established by these synthetic runs.
